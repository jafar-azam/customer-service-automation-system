## 3. Conflicts and corrections

Where I am deviating from the letter of the specification, or from a research recommendation, with
the reason. Nothing here is a silent change.

**3.1 The research's recommended generation models are not free-local.** `arabic-data.md` names
GPT-4.1-mini and Jais-2-70B-Chat as the evidence-backed pair for generating Lebanese query
variants. Neither is free, and neither runs on an 8 GB laptop GPU. Your cost rules win. So:
Lebanese variant generation (step 19) runs as an **offline, one-time notebook** with a
free open-weight model that fits the 3070 (Jais-2-8B-Chat Q4, ~5.5 GB, officially Apache-2.0 with
an official GGUF per `ml-training-adjacent.md`), **not** at request time; the runtime application
never needs it. The research's own warning applies and will be reported honestly: an 8B model will
produce weaker dialect than the 70B it benchmarked, which raises the native-reviewer rejection rate
and lowers the accepted-example yield. The native review gate (step 20) is what makes the dataset
trustworthy, not the generator — so a weaker generator costs reviewer time, not data quality.

**3.2 "Answer only from the KB" does not need a strong LLM, and that is the point.** The runtime
assistant is a grounded RAG reader: retrieve, then answer from retrieved text with citations, or
escalate. The default provider is a **deterministic mock** that composes the answer from the
retrieved KB entries and cites their IDs — it makes every test pass with zero keys, and it is also
a legitimate degraded mode. The optional real provider is a **local Ollama** model (default
`qwen3:4b` Q4, ~2.6 GB, runs on CPU or the 3070; `jais2:8b` for Arabic-quality demos). No paid
provider is wired, only the documented interface.

**3.3 The human test set: 150–200 items is below what the research says it takes to make the claim
you will want to make.** `arabic-data.md` computes it: ±5 percentage points at 95% confidence needs
~385 independent cases, and it proposes ~1,600 (≈400 per writing mode). With 200 items split five
ways, each per-input-form number carries roughly ±14 points — wide enough that "Arabizi performs
worse than MSA" would usually not be a statement the data supports. I am building to your number
(200, the top of your range, ≈40 per input form) because collecting 1,600 human-written questions
is not realistic for this release, **and** the evaluation script will print 95% confidence
intervals next to every per-form number, with `docs/evaluation/README.md` stating plainly that
per-form differences are indicative, not significant. The fairness check in section 6 of the spec
("flag any form that performs significantly worse") is implemented as a test on the interval, not
on the point estimate — a wide interval reports "insufficient evidence", not a false alarm.
Growing the set past 385 is the first item in the roadmap's evaluation section.

**3.4 Two things in this project cannot be synthesized, and both need people.** The human test set
(150–200 questions, by definition never generated) and the native-speaker review queue (step 20)
require real Lebanese speakers. I will build: a collection kit (a simple form, scenario cards so
authors write from facts rather than paraphrasing, consent text, an anonymization pass, an importer)
and the review UI with reviewer-agreement tracking. I cannot supply the people. The repo must
therefore ship with a small **seed** of these sets and an honest count — `docs/evaluation/README.md`
will say exactly how many human items exist and who wrote them. Plan for it early: collection can
run in the background from Phase 6 onward while I build Phase 7–11.

**3.5 Mandatory admin TOTP vs "a reviewer logs in within five minutes".** These fight. A reviewer
who clones the repo has no authenticator seeded. The resolution I propose (question asked
separately): a `DEMO_MODE` flag, default on in the local Compose stack and **hard-refused when
`NODE_ENV=production`**, that seeds the demo admin with a fixed documented TOTP secret and shows
the current 6-digit code in the dev-inbox page. The 2FA code path stays mandatory and fully tested;
only the secret's provenance is demo-only, and a test asserts the flag cannot be enabled in
production.

**3.6 MongoDB needs to be a single-node replica set, not a standalone.** Multi-document
transactions (refresh-token rotation + session-family revocation + audit log must commit or fail
together) and change streams both require a replica set. Cost: one `rs.initiate()` in a Compose
init container. Standalone would force me to write compensating logic for exactly the flows where
correctness is a security property, which is the wrong trade.

**3.7 Lighthouse ≥95 applies to public pages only** (as your spec says) — the dashboard is excluded
from the budget and is where the lazily-loaded chart library lives. I will state the exclusion in
`docs/performance/README.md` rather than quietly measuring only the easy pages.

**3.8 The Privacy page is a demonstration notice, not a privacy policy.** `privacy-law.md` is
explicit: its template is a *structure*, several Lebanese questions are unverified, and the
recommended boundary for a portfolio is a clearly-labelled demo on synthetic data. The page will
follow the report's section structure, describe what this system actually does, and carry a visible
banner that it is an educational artefact requiring legal review before real use. The
lawyer-confirmation list is reproduced in `docs/security/PRIVACY.md` as open questions.

**3.9 ASVS Level 2 is a target, not a certification.** `docs/security/CHECKLIST.md` maps each
requirement to the code and the test that proves it, and marks anything unmet as unmet. No claim of
compliance appears in the README.

- **Splitting by incident family / lineage ID**, never by row, with cross-language and
  paraphrase-family grouping, MinHash + embedding near-duplicate audits across splits, and the human
  test set frozen and never used for training or threshold tuning.

### 4.3 ML plan (Phase 7)

Baselines first and always reported: TF-IDF + logistic regression for classification; the base
(not fine-tuned) embedding model for retrieval. Then (a) intent/topic classifier on an
Arabic-capable encoder, (b) escalation classifier over retrieval scores + text features with
**calibrated** probabilities and a risk–coverage curve to pick the threshold, (c) contrastive
embedding fine-tune with hard negatives across all five input forms, measured by solution-level
Recall@5/MRR against the base model. The LoRA experiment (26) is **skipped per your scope** and
recorded in the roadmap. Artefacts are safetensors/ONNX with recorded hashes verified before
loading — no pickle, ever. Tracking with fixed seeds and saved configs, a model registry, a model
card per model with metrics **broken out per input form**, and promotion gated on beating the
incumbent on both held-out and human test sets with no per-form regression, after shadow
evaluation, with admin approval and one-click rollback. Primary reported number, per
`arabic-data.md`: **false-answer rate on cases that should escalate** — not average answer quality.

### 10.1 Licence — a correction to the research

`datasets.md` records TechQA as **Apache-2.0**, cited from the GitHub repository's `LICENSE.md`.
That is the licence on the *code*. The data ships under **Community Data License Agreement –
Permissive, Version 1.0** (`CDLA-Permissive-v1.0.pdf` in the archive, confirmed by `README.txt`,
and the technote corpus is released separately under the same licence).

This is still good news and does not change the plan's direction: CDLA-Permissive-1.0 permits use,
modification and redistribution of the data **and of derived data**, with no ShareAlike obligation
on results such as trained models — provided the licence text and disclaimers travel with any data
you redistribute. So a curated derived KB subset **can** be committed, with the licence file,
attribution and per-record provenance. The 12 GB original stays out of git and is fetched by script.
`docs/ml/LICENSES.md` (step 05) records CDLA-Permissive-1.0, not Apache-2.0, and the step 37
third-party report inherits the corrected value.

One caveat `datasets.md` raised that still stands: these are real IBM support technotes and
anonymization was never verified upstream. Usernames, hostnames, paths and environment details do
appear in question bodies. The PII/secret pass in step 19 therefore runs over the committed subset
as a gate, not as a formality.

### 10.2 What is actually in the archive (measured, not from the README)

| | Instances | Answerable | Unanswerable |

| `training_Q_A.json` | 600 | 450 | 150 |
| `dev_Q_A.json` | 310 | 160 | 150 |

- Each question carries **50 candidate technotes** in `DOC_IDS` — a realistic retrieval task, and a
  pool of **human-selected hard negatives**.
- Answerable instances give `DOCUMENT` + `START_OFFSET`/`END_OFFSET` + the extracted `ANSWER`

- 28,482 technotes in the train/dev subset; median body 3,060 chars, p90 6,577, max 178,280 →
  chunking is required. Metadata gives `productName` (1,129 distinct), `productId`, `date`,
  `canonicalUrl`. Top products are WebSphere Application Server, WebSphere MQ, DB2, WebSphere
  Portal, Netcool/OMNIbus, SPSS — enterprise software under support contracts, which is this
  product's exact domain.
- The full corpus (801,998 technotes, 6.4 GB JSON) is not needed and will not be touched by the
  pipeline.
- **The README is slightly wrong:** it documents `QUESTION_BODY`, the files actually contain
  `QUESTION_TEXT`. The importer reads the real field and the step 05 README notes the discrepancy.

### 10.3 What this changes

1. **The KB seed stops being synthetic.** Step 05 imports **621 real question→grounded-resolution
   pairs** (450 + 160 + 11) with verifiable answer spans, instead of a synthetic KB. Grounding goes
   from "trust the generator" to "compare the cited span against the gold span" — the citation check
   in step 15 and the grounding metric in step 21 become *measurable* rather than asserted.
2. **The escalation benchmark becomes real and in-domain.** 309 genuinely unanswerable support
   questions, annotated by humans as unanswerable from the candidate documents. `datasets.md`
   recommended CLINC150's generic out-of-scope set as the fallback; this is strictly better, because
   these are real technical questions that happen to have no answer in the KB — exactly the case
   where a false answer is most dangerous. CLINC150 drops to a secondary comparison.
3. **Hard negatives come free, and they are real.** Step 25's contrastive embedding fine-tune needs
   hard negatives; the 49 non-answer candidates per question are human-curated near-misses. No
   mining heuristic to defend.
4. **Honest scale, stated up front.** `datasets.md` proposes 3,000 approved problem–resolution
   records for a "credible demo", but that target assumed *synthetic* generation from project-owned
   procedures. Using real grounded data instead trades volume for verifiability: ~620 solutions,
   ~2,500 generated query variants across the four Arabic/Arabizi/code-switch/MSA modes (step 19),
   309 real escalation cases, and the 200-item human test set (step 21). The README will report
   those numbers plainly rather than padding the KB with synthetic entries to reach 3,000.
5. **The five input forms still work the same way.** TechQA is English. The MSA translation of each
   resolution and the four query-variant modes are unchanged from §4.2 — TechQA supplies the
   *solutions* and the English stratum; step 19 supplies Lebanese Arabic, Arabizi, code-switching
   and MSA queries against them; step 20 gates them on native review.
6. **`seniordata.csv` stays as planned** — local-only, never committed, never in a training split
   (§9). TechQA replaces it as the publishable seed, which resolves the §1.3 problem entirely.

### 10.4 Training runs on this laptop — confirmed

Phase 7 trains on the RTX 3070 (8 GB). Colab/Kaggle notebooks are still delivered because a
reviewer without a GPU must be able to reproduce the results, but they become the alternative path,
not the primary one. Budgets to verify at step 22:

| Model | Approach | VRAM | Rough time |
| :-- | :-- | --: | :-- |
| Intent/topic classifier (23) | fine-tune an Arabic-capable encoder (110–280 M params) | 3–5 GB | minutes |
| Escalation classifier (24) | gradient boosting / logistic regression over retrieval + text features, then probability calibration | CPU | seconds |
| Embedding fine-tune (25) | contrastive, `multilingual-e5-base` (278 M), in-batch + TechQA hard negatives, gradient checkpointing | 6–7 GB | tens of minutes |
| Voice evaluation (28) | `faster-whisper large-v3` int8 | ~4.5 GB | realtime-ish |
| Lebanese variant generation (19) | Jais-2-8B-Chat Q4 via Ollama, one-time offline | ~5.5 GB | hours, batched |

`e5-large` (560 M) is kept as a *frozen* retrieval baseline rather than a fine-tune target —
contrastive learning wants large batches, and 8 GB would force batches small enough to hurt the
result more than the extra capacity helps. That is a measurement to report, not an assumption, so
step 25 records both. Step 22 first verifies CUDA actually reaches PyTorch through WSL
(`/usr/lib/wsl/lib`), since that is the usual failure point.
