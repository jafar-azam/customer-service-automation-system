# Step 12 — Attachments

**Phase 4. Status: complete and verified** against the test suite and the
running Compose stack on 2026-10-25.

## Goal

Let a customer send a screenshot of the error, and an agent read it, without
that becoming the way malware or a customer's home address enters the system.

This is the most security-dense step in the phase. Seven checklist items close
here (7.1–7.6 and 4.3), and one — the retention sweep — is handed to step 14.

## 1. What was built

```
apps/server/src/services/
├── providers/storage.ts          private store, server-generated keys
├── providers/virus-scan.ts       ClamAV + a mock that detects EICAR
└── attachments/
    ├── type-check.ts             magic bytes, allowlist, safe filenames
    ├── sanitize.ts               re-encode, metadata and payloads destroyed
    ├── signed-url.ts             short-lived, bound to file and subject
    ├── fixtures.ts               real images, generated by a real encoder
    └── index.ts                  the order of operations
routes/attachments.ts             upload, link, download
apps/server/Dockerfile            the store, owned by the user that writes it
```

---

## 2. The order of operations is the security property

```
1. ownership check      — before the bytes are touched at all
2. size and count       — before anything reaches a decoder
3. identify by bytes    — never by Content-Type or extension
4. re-encode images     — metadata and appended payloads destroyed
5. scan                 — on the bytes that will actually be stored
6. store                — under a server-generated key
7. record               — with its retention date
```

Scanning before sanitising would scan bytes nobody will ever serve. Storing
before scanning would put an unscanned file in the store, and a crash between
the two would leave it there forever. An ownership check anywhere later would
mean a stranger's upload gets decoded before being refused.

## 3. Decisions, and what each one costs

### 3.1 The allowlist is short, and applied to the detected type

JPEG, PNG, WebP, PDF, plain text. That is what a support conversation needs.

`shell.php` renamed to `holiday.jpg` arrives with a `.jpg` extension and
`Content-Type: image/jpeg`. Both are strings the client chose; neither is
evidence. The signature decides, and the allowlist is applied to **that**.

Deliberately absent, each for a reason:

- **SVG** is not an image, it is a document with a `<script>` element.
  Rendering one in our origin is stored XSS, and sanitising SVG is a losing
  arms race. The customer can send a PNG.
- **Archives** hide their contents from every check here, and a scanner that
  unpacks them inherits the decompression-bomb problem.
- **Office documents** carry macros. **HTML** is the vector with no disguise.

Even **GIF** is refused — it decodes perfectly well. The allowlist is the list
of formats whose risk is understood, not the list of things that parse.

### 3.2 Text is the one type decided by exclusion, so the exclusion is strict

Text has no signature. A NUL byte anywhere disqualifies it, it must decode as
UTF-8 with no replacement characters, and the only control characters allowed
are tab, newline and carriage return. Without that strictness, "unknown binary"
quietly becomes "text/plain".

A `.txt` whose first bytes are `<script>` is also refused. It is served as
`text/plain` with `nosniff` and `Content-Disposition: attachment`, so it should
not matter — but it is not a log file anyone needs to attach, and refusing it
costs a customer nothing.

### 3.3 Re-encoding does three jobs, and the third is the one people forget

1. **Metadata is gone.** EXIF carries GPS, the device serial and the capture
   time. A customer photographing a broken printer sends their office location
   without knowing it.
2. **Appended payloads are gone.** A PNG stays a valid PNG with a PHP script
   concatenated after its end marker. Only decoded pixels survive.
3. **The file is remade by a decoder we chose.** A file crafted against one
   specific viewer no longer has its crafted bytes.

Everything comes out as PNG: one output format means one decoder on the way
back out, and it sidesteps "which JPEG quality is enough to read an error
message in a photograph". Re-encoding is lossy for JPEG, and that is an
accepted cost for a support attachment.

### 3.4 The mock scanner still works

ClamAV is behind `--profile scan`, because a 1.5 GB signature database is not
something the default stack should pull. The **mock is the default and still
detects EICAR**, by hash rather than by content — storing the literal would
make this repository un-clonable on a managed laptop.

That detail is the point. A mock that always answers "clean" makes the infected
branch unreachable and untested, and nobody finds out until production that the
quarantine path throws.

**`pending` and `error` are refused alongside `infected`.** A scan that failed
to run is not a scan that passed; treating "we could not tell" as clean is how
a scanner outage becomes a malware delivery service.

### 3.5 A signed URL is not an access control

The download route performs the same ownership check as every other read,
through the same `findTicket` the REST and socket paths use.

The signature does a narrower job: a URL in a browser history, a proxy log, a
screenshot or a forwarded message stops working in five minutes. Both halves
are needed. A signature alone makes a leaked URL a permanent bearer token; an
ownership check alone means a link outlives the conversation it belonged to.

The token binds the attachment **and the subject it was issued to**, so one
customer's link cannot be replayed by another inside its lifetime. Expiry is
checked *after* the signature, so a forged token never reveals whether its
embedded timestamp was in the future.

### 3.6 Nothing is ever rendered inline in this origin

```
Content-Disposition: attachment
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'none'; sandbox
Cache-Control: private, no-store
```

That first header is the single most effective control against a stored-XSS
payload in an uploaded file. A separate origin would be better still, and is in
`PRODUCTION.md` — this release is single-origin.

## 4. Three bugs found by running it

The suite was green for all three.

**The attachment store was not writable.** `EACCES: permission denied, mkdir
'/var/lib/csas/storage/attachments'`. The server runs as an unprivileged user
and Docker initialises a named volume from the image's directory at that
path — including its ownership — so a directory that does not exist in the
image gets created by the daemon as root. **476 tests passed and the first real
upload returned 500.** The Dockerfile now creates it, `chown node:node`, mode
0700.

**Mounting a router at `/api` with a blanket guard broke every unknown route.**
`router.use(requireStaff(...))` runs for every request under the mount, not
only the routes the router defines — so `/api/anything` started answering 401
instead of 404, which both leaks that authentication exists and broke the
proxy's deliberate 404 on `/metrics`. Caught by the app and observability
suites. The guard is now attached per route.

**Two limits that contradicted each other.** `MAX_DIMENSION` of 8000 means 64
megapixels at square, above the 50-megapixel budget — so an image at exactly
the resize threshold could never be decoded in order to be resized. The reason
was also wrong: sharp's own limit fired and the caller was told `undecodable`
when the truth was `too_large`. Dimensions now come from the header, which is
parsed rather than decoded, so a bomb is reported as a bomb.

### 4.1 And two about the tests themselves

**The fixtures were not real files.** An eight-byte PNG signature followed by
zeros is not a PNG, and `file-type` correctly refused to call it one. Weakening
the detector to accept the fixture would have been exactly the wrong fix — a
detector that accepts a signature with no valid structure is the one a polyglot
walks through. The fixtures are now generated by sharp.

**The in-memory store leaked between tests**, so three "nothing was stored"
assertions failed against files earlier tests had legitimately stored. A store
is state like a database is state.

## 5. Security controls, and the test proving each

| Control | Test |
| :-- | :-- |
| Type from magic bytes, never the filename or header | renamed ELF, SVG, zip, GIF, offset-PDF polyglot all refused |
| Text decided strictly, not by exclusion-by-default | NUL, invalid UTF-8, control characters, `<script>` all refused |
| GPS and EXIF destroyed | fixture verified to carry GPS **before** the strip, absent after |
| Payload appended past the image data destroyed | `<?php` present in input, absent in stored bytes |
| Decompression bomb refused | 144-megapixel, 420 KB file refused as `too_large` |
| Infected file never stored | 422, store empty, no document, audit entry written |
| A scanner error is not a pass | stored but `downloadable: false`; link request → 409 |
| Upload to another's ticket | 404, and the scanner was never called |
| Signed link expires | `expired` one second past the TTL |
| …cannot be extended, re-pointed or replayed | forged/edited/wrong-subject/wrong-file all `invalid` |
| …is not enough on its own | valid link with no session → 401 |
| Never rendered inline | `attachment` + `nosniff` + sandbox CSP asserted on the response |
| Filename never becomes a path | `../../etc/passwd` → `passwd.txt` |
| Header injection via filename | CR/LF and quotes stripped |
| Audit records the type and size, never the filename | a filename is often personal (`passport-scan.pdf`) |

## 6. How to verify

```bash
npm run test -w @csas/server     # 476 tests
npm run up && npm run smoke      # 30 checks through the proxy
```

The smoke walk now includes the upload path, because that is the part most
decided by nginx rather than Express — `client_max_body_size`, request
buffering, and whether the multipart body survives the hop at all:

```
  ok   an image uploads through the proxy  — 201
  ok   it is scanned and downloadable
  ok   a renamed executable is refused  — got 415
  ok   a signed download link is issued  — 200
  ok   the file downloads through the proxy
  ok   the proxy preserves the download headers  — attachment; … / nosniff
  ok   a signed link alone is not enough  — got 401

smoke: all 30 checks passed
```

To exercise the real scanner: `docker compose --profile scan up -d clamav` and
set `FILE_SCAN_PROVIDER=clamav`. It costs about 2 GB of RAM.

## 7. What this step does not do

- **No retention sweep.** Every attachment carries a `deleteAfter` 365 days
  out; nothing deletes yet. Step 14.
- **No virus re-scan.** A file scanned clean today with a signature database
  from today stays clean forever as far as this code is concerned.
- **PDFs are not re-encoded.** They are the one format served as uploaded,
  which is why they are served as a download and never rendered inline. A PDF
  sanitiser is in `PRODUCTION.md`.
- **Single origin.** Serving attachments from a separate origin would be
  stronger than `Content-Disposition` alone.
- **No client UI.** The endpoints exist; no screen uses them until step 13.
- **No thumbnails**, and no streaming — a 10 MB cap means the whole file fits
  in memory, which keeps the scan-before-store ordering simple.
